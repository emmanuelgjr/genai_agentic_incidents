## 1. What was implemented, and why it diverges from §5.3's literal example

§5.3's own example reference shape is `{"title": "OECD (<year>), ...", "url":
"<page-url>", "type": "citation"}` — **added** as a new list entry. This
implementation instead **retitles the existing OECD-page reference in
place**, matched by URL rather than by position, and uses `"type":
"reference"` rather than `"citation"`. Both divergences are deliberate, not
oversights — §5.3 itself invites this ("*or wherever this repo's render
layer already surfaces such citations for other sources*"):

1. **`"citation"` is not a valid `references[].type`.**
   `schema/incident.schema.json`'s enum is `["news", "advisory", "research",
   "vendor", "blog", "cve", "report", "paper", "video", "podcast",
   "regulatory", "disclosure", "documentation", "legal", "analysis", "arxiv",
   "exploit", "patch", "reference", "threat-report", "other"]` — no
   `"citation"`. Per this task's own constraint ("if a schema change is
   needed, STOP and report"), adopting the literal example would either
   require a schema change (schema-architect's exclusive domain) or ship
   schema-invalid data. `"reference"` is already in the enum and is already
   `export_stix.py`'s own default fallback for an untyped reference
   (`scripts/export_stix.py:125`) — the closest existing "this is just a
   citation-style link" value.

2. **Retitling in place, not appending, is required for the count to
   actually land on all 3,829 rows — not just today, but durably.**
   `merge_into()` (the cross-entry-merge reference union) dedupes
   `references` by URL — a dict keyed on `normalize_url`, later entries
   overwrite earlier ones on collision
   (`scripts/merge_and_dedupe.py:1808-1814`, unchanged by this batch). A
   *second* reference entry pointing at the identical `oecd.ai` page URL is
   not guaranteed to survive a future cross-entry merge: whichever of the
   two same-URL titles happens to land last in iteration order wins, and the
   other silently disappears. This is exactly the collision risk the
   dispatching brief flagged ("verify empirically what actually lands; do
   not assume") — retitling the ONE reference that already carries that URL
   removes the collision **structurally**, not by observation of today's
   merge order. See §4 for the empirical count that confirms this.

3. **Position matters and must be found by URL, not assumed to be
   `references[0]`.** `render_markdown.py`'s "Cite this incident" line reads
   `references[0]`. E23 measured that AIID's own citation link sits at
   `references[0]` for 1,463/1,465 AIID rows — a property this batch must
   not perturb. Measured here (§5): **only 3,667 of the 3,829 OECD-AIM rows
   have their OECD page reference at position 0** — the other 162 were
   merged into an AIID entry whose own citation claimed slot 0 first.
   Matching by URL (`^https://oecd\.ai/en/incidents/`) finds the right
   reference in either case and never reorders the list, so AIID's own
   `references[0]` property is left untouched (confirmed unchanged: still
   1,463/1,465, §6).

## 2. Where the code lives, and why there's no separate migration script

Unlike the E21 narrative reduction (which needed a one-off
`scripts/migrate_oecd_description_reduction.py` because `description` is
computed once at ingest/normalize time and frozen into the committed
`ingest/oecd_aim_full_incidents.json`), this fix needs no separate migration
script. The value it depends on — `entry["added"]`, this project's own
first-ingest date for the row — is **only known during `merge_and_dedupe.py`'s
build-time reconciliation** (`_apply_history()`), not at ingest time. So the
fix lives entirely in `scripts/merge_and_dedupe.py`, called from inside
`_apply_history()` immediately after `entry["added"]` is set (both branches:
brand-new row and already-committed row), and *before*
`_content_snapshot()` is taken:

```python
_OECD_PAGE_URL_RE = re.compile(r"^https://oecd\.ai/en/incidents/")
_OECD_PAGE_URL_DATE_RE = re.compile(r"^https://oecd\.ai/en/incidents/(\d{4})-\d{2}-\d{2}-")

def _oecd_citation_title(url, fallback_year, accessed_on):
    m = _OECD_PAGE_URL_DATE_RE.match(url)
    year = int(m.group(1)) if m else fallback_year
    return f"OECD ({year}), AI Incidents and Hazards Monitor, {url} (accessed on {accessed_on})"

def _apply_oecd_attribution(entry):
    accessed_on = entry.get("added")
    if not accessed_on:
        return
    for r in entry.get("references") or []:
        if isinstance(r, dict) and _OECD_PAGE_URL_RE.match(r.get("url") or ""):
            r["title"] = _oecd_citation_title(r["url"], entry.get("year"), accessed_on)
            r["type"] = "reference"
```

Because `merge_and_dedupe.py` reprocesses the **entire** committed
`ingest/oecd_aim_full_incidents.json` (4,160 rows) on every build — not just
a delta — this single code path covers both the forward path (a fresh OECD
ingest tomorrow) and the retroactive path (every row already committed)
without needing two locations kept in sync by an import, the way the
narrative reduction did. There is only one path, by construction, so it
cannot drift.

**`accessed_on` is never "today."** It is `entry["added"]`: for an
already-committed row, `_apply_history()` sets `entry["added"] =
prev_added` (the row's own historical first-ingest date, read from the
previous build's committed output) *before* `_apply_oecd_attribution` runs —
so the citation always cites the date this pipeline genuinely first pulled
the page, never the date this particular rebuild happened to run. Only a
genuinely brand-new row (no previous entry to inherit `added` from) gets
`entry["added"] = today`, which is correct: that IS the day it was
first accessed. Measured on the current corpus (§4): the citations in
production use **9 distinct accessed-on dates spanning 2026-05-11 to
2026-07-19** — evidence this is reading real historical `added` values, not
uniformly stamping the day this batch ran (2026-07-31, per `utc_today()`;
today is UTC-past-midnight relative to the 2026-07-30 session date).

**Gating.** Deliberately gated on the reference's own URL matching
`oecd.ai/en/incidents/`, not on `OECD-AIM-` appearing in `source_ids`.
`ingest_external.py::ingest_aiid_oecd_bridge()` places an `oecd.ai` page URL
directly onto AIID entries it cross-links (source_id `AIID-<id>-OECD`,
canonicalised to plain `AIID-<id>` and merged into the AIID entry proper)
without ever contributing an `OECD-AIM-` source id. Gating on `source_ids`
would have silently missed those; gating on the URL catches every row that
actually displays an OECD page link, which is the property that matters.

## 7. Determinism

```
python scripts/parse_existing.py && python scripts/merge_and_dedupe.py   # run 1
python scripts/parse_existing.py && python scripts/merge_and_dedupe.py   # run 2, no input changes
python -c "import json; a=json.load(open('run1/data/incidents.json')); b=json.load(open('data/incidents.json')); print(a == b)"
# True
```

A second consecutive rebuild with no new inputs is byte-identical —
`updated` does not re-bump on repeated rebuilds, because the citation title
is a pure function of `added` (stable, looked up from the previous build)
and the row's own already-committed fields, never of the day the rebuild
happens to run on. This is also covered as an enforced regression test
(`test_oecd_attribution_bumps_updated_once_then_is_stable`, §8) rather than
only checked ad hoc here.

`make build` performed zero network calls and zero model calls throughout —
every step (`parse_existing.py`, `merge_and_dedupe.py`, `render_markdown.py`,
`render_docs_stats.py`, `validate.py`) reads only committed snapshots and
the previous build's own output.

**Pre-existing test-infra note, not fixed here (out of this task's scope):**
this file's existing `_FrozenDate`/`monkeypatch.setattr(m, "date", ...)`
pattern (used by `test_build_is_deterministic_across_days` and others)
patches the `date` class, but `utc_today()` calls
`datetime.now(timezone.utc).date()` — a different name, never affected by
that patch. The existing tests using it happen to still pass because they
only assert `day1 == day2` (relative equality across two builds), never a
literal date value, so the patch being inert doesn't currently cause a false
pass. My two full-build tests needed to assert a literal date, so they
monkeypatch `m.utc_today` directly instead (`_freeze_utc_today` helper).
Flagging for awareness in case a future test wants a literal date and
reaches for the existing pattern expecting it to work.
