## Licensing and provenance

### Row-level content-licence marking
**1,517 AIAAIC-derived rows** (100% of AIAAIC-sourced rows currently in the
corpus) now carry a machine-readable `content_license` object (CC BY-SA
4.0, with attribution and obligation fields), mirrored into the STIX export
as `x_content_license`. Rationale: `docs/audits/WS0-E13-database-right-2026-07-18.md`,
`docs/audits/WS0-T3-cascade-2026-07-18.md`. Full per-source licensing status
— outreach state, pending/resolved counts, the running per-source
determination — lives in `docs/SOURCE_LICENSES.md` and `NOTICE-DATA` and
this document does not restate it (D24). What this document does state are
figures about *this release specifically* — what changed, on how many
rows, this window — which is a different thing from a per-source status
table and is exactly what a release's own notes exist to disclose.

### AIAAIC — facts, not narrative
AIAAIC-derived rows carry structured facts (system, technology, sector,
jurisdiction, affected) and a source pointer rather than AIAAIC's own
narrative/descriptive cell text, disposing of the copyright share-alike
question over that text (decision D2). The retained AIAAIC headline is
tracked as a separate, still-open question — see `docs/SOURCE_LICENSES.md`
§1.1 and the E15/D17 audits.

### OECD AI Incidents and Hazards Monitor (AIM) — `description` reduced, `title` still open
OECD AIM's own methodology page states its per-event `title` and `summary`
metadata is **LLM-generated (OpenAI o3-mini) from third-party news
articles** — not OECD staff prose, not quoted news text either
(`docs/audits/E21-oecd-narrative-licence-2026-07-30.md` §2.4). Per that
finding:

- **`description` on OECD-AIM-sourced rows is reduced to structural facts
  and a source link** — never AIM's LLM-generated narrative. Measured on
  the shipped corpus: **3,667 of the 3,829 OECD-AIM-sourced rows** carry
  the reduced description (the other 162 ship a different upstream
  source's description instead, because that source won the entity-merge —
  disclosed, not a miss). Applied retroactively to all already-committed
  rows via a one-off local transform, no re-fetch, no model call.
- **`title` is explicitly NOT covered by this reduction, and this is not
  silent: it still ships the same LLM-generated text verbatim on 3,667 of
  those same 3,829 rows** (the other 162 ship a different source's title,
  for the identical entity-merge reason as `description` — independently
  confirmed to be the *same* 3,667-row set, not a separately-drifting
  count). **Any release description implying OECD `title` text was removed
  or resolved this window is false.** It is tracked as a separate, open
  question at the same posture as AIAAIC's retained-headline question
  (E15/D17), not resolved here.

  > this same 3,667/162, as of `8afa39c0` (corrected after this draft's
  > cross-validation surfaced that both had been reading one row's title
  > against only the *first* of its OECD-AIM source IDs, overcounting the
  > residue by one). The cross-validation that caught it holds independent
  > of that fix and is worth keeping on the record: 3,667/162 is confirmed
  > four separate ways — a string-match against the raw OECD ingest

  > own before/after diff; the "OECD citation at `references[0]`" row set

  > `merge_into()` never touches `title` or `description` — both fields

### OECD AIM — per-entry attribution now lands on every sourced row
**All 3,829 of 3,829 OECD-AIM-sourced rows** now carry a per-entry citation
reference (`OECD (<year>), AI Incidents and Hazards Monitor, <page-url>
(accessed on <date this project first ingested the row>)`), regardless of
which description/title the row ships. An additional 368 rows that absorbed
OECD-AIM content into a merged AIID entry (no `OECD-AIM-` source ID of
their own) also carry the citation, for 4,197 rows total with a
citation-shaped reference.

**One nuance worth stating precisely, because "at position 0" and
"rendered as the citation line" are not the same claim:** the citation
lands at `references[0]` (and so becomes the page's "Cite this incident"
line) for **3,667 of the 3,829** rows. The **one** exception is
`INC-00437`: its OECD reference sits at `references[0]`, but because the
row also carries an `aiid_id`, `render_markdown.py` prefers the AIID
citation link for the "Cite this incident" line regardless of reference
position — correct, documented render behavior (E23), not a miss. So
**3,666 of 3,829** rows actually render the OECD citation as their "Cite
this incident" line; the OECD citation still appears in all 3,667 rows'
References list either way.

### AIID — official snapshot channel, and the content-licensing question resolved
AIID ingestion now reads AIID's own weekly snapshot channel rather than the
former high-volume scraper (retired), with a committed pinned-provenance
record (`docs/audits/WS0-T4-aiid-snapshot-swap-2026-07-18.md`). AIID's
license-excluded `reports.text` is never opened.

**AIID-derived rows carry no `content_license` marker — 0 of 1,466** (the
union of every AIID-identifying signal: `aiid_id`, an `AIID-`-prefixed
source ID, or an `incidentdatabase.ai` reference URL — not the narrowest
count). **That is a resolved decision, not a gap.** AIID's maker is
US-situated; under US law the only AIID text this dataset ships (`title`)
is categorically excluded from copyright (Circular 33 / 37 C.F.R.
202.1(a)), and a US-situated maker also fails both the UK (reg 18) and EEA
(Art 11) sui generis database-right qualification tests, so no such right
subsists in AIID's collections at all. Full reasoning:
`docs/audits/E23-aiid-marking-ruling-2026-07-30.md`.

**This is why AIID and AIAAIC are marked differently** — not two postures
toward the same question, but two legal systems answering the identical
question differently. AIAAIC's UK situs has no equivalent categorical rule,
so its question (§1.1/E13) stays open.

**The tripwire.** This ruling clears only the population that actually
ships. A separate, dormant population — hand-curated rows in
`ingest/aiid_incidents.json` that collide by AIID ID with the official
snapshot, and AIRI Navigator rows carrying their own AIID-derived title —
is kept out of the shipped corpus **only by current merge order and
source-ID dedup precedence**, not by any content review. It is not covered
by this ruling; if it ever starts shipping, that merge-order protection
does not carry over and the population needs its own review first. This is
no longer just a documented caveat — it is an enforced regression test,
`tests/test_e23_aiid_dead_letter_tripwire.py`, which fails the build if a
future change (an alphabetical file-rename, a dedup-precedence change, an
`aiid_id` allow-list edit) ever lets that population's own title or
description leak into what ships.

### Orphaned ingest file retired
`ingest/oecd_aim_incidents.json` — an 86-row hand-curated OECD file with no
producing script and no other code reference, silently shipping rows since
it was orphaned on 2026-05-13 — has been retired. **59 of its 86 rows were
the corpus's only source for that incident and are now gone** (tombstoned,
`into: null` — see ["Consumer impact"](#consumer-impact-the-59-tombstoned-ids)).
The remaining 27 were already cross-covered by AIID or OECD-AIM proper and
simply lost the orphan file's contributed `source_ids`/`tags`/framework
mappings on rebuild — disclosed and justified in
`docs/audits/E21-reduction-delta-2026-07-30.md`, not part of the narrative
reduction itself. One row's classification changed as a direct, verified
consequence (`INC-08170`: `security` → `ai-harm`, correcting the
classification, not degrading it — same audit, §6).

## Freshness honesty

**1,380 rows** derived from a source whose feed went stale on 2026-05-31
now carry a `source_freshness` object (`status`, `as_of`, `sources`).
`active`/no marker means *emitted, not necessarily live* — `status: stale`
on these 1,380 means the project knows and is disclosing it, not that the
data is wrong. Field reference: `docs/DATA_DICTIONARY.md`. A published
source-freshness registry (`data/source_freshness.json`) declares which
copy of the upstream health counter it was reconciled against, and
`validate.py` holds it to that specific claim rather than to "current" —
reporting **VERIFIED**, **NOT COMPARABLE HERE**, or **FAILED**
distinguishably.

## Ingestion conduct

All HTTP(S) fetching in this project's ingest scripts routes through a
single module (`ingest/common.py`), which enforces an identifying
User-Agent, a fail-closed robots.txt check, and per-host rate limiting —
with **one enumerated, evidenced host exception**
(`ROBOTS_UNVERIFIABLE_ALLOWLIST`, documented with its justification in
`docs/INGESTION_CONDUCT.md`). Non-HTTP egress (`gh api graphql`, vendor
CLIs) is **registered** with its conduct properties, not exempted from
disclosure. `docs/INGESTION_CONDUCT.md` states what the code actually
enforces, including one disclosed gap.

## ⚠ If you consume v2.7.0 or v2.8.0 AIAAIC-derived rows

Both releases shipped before this window's licensing work. If you pulled
**AIAAIC-derived rows** from `v2.7.0` or `v2.8.0`, you have pre-marker,
pre-reduction data: no `content_license` field, and possibly AIAAIC's
narrative cell text that this window's work replaces with facts-plus-link.
Re-pull rather than diffing against those releases for AIAAIC-derived rows.

AIID- and OECD-derived rows from those earlier releases are not affected in
the same way (no retroactive removal of previously-shipped text), but the
new `content_license`/attribution/`source_freshness` fields are new schema
additions, so an old row you're holding will simply lack them until
re-pulled.
